# Тижневий звіт про зустрічі (Lab 5)

Щопонеділка о 07:00 (Europe/Kyiv) система будує CSV-звіт за минулий ISO-тиждень, кладе його
в S3 і надсилає на пошту через SES. Ніхто нічого не натискає.

```
EventBridge Scheduler ─┐                         ┌─ report-builder (Lambda у VPC, образ бекенду)
                       ├─► SQS report-requests ──┤     читає RDS, пише reports/<week>.csv
make report-now ───────┘      │ 3 спроби          │     в S3 через gateway endpoint
                              ▼                   ▼
                       report-requests-dlq      S3 ──ObjectCreated──► report-mailer (Lambda поза VPC)
                                                                           └─► SES ─► пошта
```

| Файл | Що в ньому |
|---|---|
| `backend/app/reports/weekly.py` | сам звіт, без AWS: `build_weekly_report(week) -> bytes` |
| `backend/app/reports/lambda_app.py` | обробник builder-а: SQS-повідомлення і прямий виклик |
| `infra/reports.yaml` | бакет, S3 endpoint, черга + DLQ, розклад, обидві функції (mailer — inline), SES |
| `infra/deploy-reports.sh`, `report-now.sh`, `report-logs.sh`, `destroy-reports.sh` | команди `make` |
| `backend/tests/test_reports.py` | тести звіту і повернення невдалого повідомлення в чергу |

Відмінності від умови лаби:
- **RDS PostgreSQL замість Aurora** (Free plan не дозволяє Aurora), тому база не «засинає», і
  builder не чекає ~15 с на її пробудження. Таймаут 60 с усе одно лишено.
- **Регіон eu-central-1**, а не us-east-1 (так задеплоєно все з Lab 2).
- **SES-ідентичність — адреса пошти, а не домен**: власного домену немає. Відправник і
  отримувач — одна підтверджена адреса (у sandbox SES так і треба).
- **Builder запускається через Lambda Web Adapter**, який уже є в образі бекенду: він передає
  SQS-подію як `POST /events` у маленький FastAPI-застосунок `app.reports.lambda_app`.
  Невдале повідомлення повертається в чергу через `batchItemFailures`.

Команди:

```bash
make report-local WEEK=2026-W41   # звіт з локальної бази (docker compose)
make deploy-reports               # розгорнути (після make deploy-backend)
make report-now WEEK=2026-W41     # побудувати і надіслати зараз
make report-ls                    # aws s3 ls s3://<bucket>/reports/ --recursive
make report-logs                  # рядки логів: яка подія запустила кожну функцію
```

## Відповіді на питання Step 7

**Скільки листів, якщо надіслати той самий тиждень двічі?** Два. Builder ідемпотентний:
обидва рази він перезаписує той самий файл `reports/2026-W41.csv`. Але S3 генерує подію
`ObjectCreated` на кожен запис, зокрема на перезапис, і mailer на кожну подію надсилає лист.
Запис файлу ідемпотентний, надсилання листа — ні.

**1. Mailer отримав ту саму подію двічі, людина — два однакові листи. Де зберігати «вже
надіслано» і який ключ?** У таблиці DynamoDB (mailer поза VPC і до RDS не дістається, а
DynamoDB доступна без VPC). Перед відправкою — умовний запис
`PutItem(... ConditionExpression="attribute_not_exists(pk)")`; якщо умова не виконалась, лист
уже надсилали, і mailer виходить. Ключ: `bucket + key + ETag` (або `versionId`, якщо в бакеті
увімкнено версіонування) — тоді повтор тієї самої події відсікається, а свідомо перебудований
звіт з іншим вмістом (інший ETag) надсилається. Якщо ж потрібно «один лист на тиждень на
людину» незалежно від вмісту, ключ — `week + recipient`. Додати TTL, щоб таблиця не росла.

**2. Builder у VPC не дістається до SES. Три способи і їхня ціна на місяць (eu-central-1):**
- **NAT Gateway:** ≈ $0.052/год × 730 ≈ **$38/міс** + $0.052 за кожен ГБ трафіку. Дає вихід в
  інтернет усьому у VPC.
- **Interface VPC endpoint для SES:** ≈ $0.012/год за кожну AZ; на 2 AZ ≈ **$17.5/міс** +
  $0.01/ГБ. Дає доступ лише до SES.
- **Поділ на дві функції через подію S3 (те, що зроблено):** gateway endpoint для S3
  безкоштовний, Lambda-виклики в межах free tier — **≈ $0**.
- *Десять листів на тиждень більше:* поділ, бо платити $17–38 щомісяця за кілька листів
  безглуздо. *Мільйон:* SES коштуватиме ≈ $100 незалежно від мережі, а фіксовані $17–38 стануть
  дрібницею; поділ і далі працює (S3-події масштабуються), тож я б його лишив. Interface
  endpoint варто брати, коли функціям у VPC треба більше AWS API, ніж S3, — а NAT лише тоді,
  коли треба ходити до сторонніх сервісів в інтернеті (наприклад, до LLM API).

**3. Посилання, що працює тиждень, замість вкладення.** Presigned URL живе не довше за облікові
дані, якими його підписано; тимчасові ключі ролі Lambda спливають через кілька годин. Варіанти:
- підписувати ключами окремого IAM-користувача з правом лише `s3:GetObject` на `reports/*`
  (довгоживучі ключі в Secrets Manager/SSM). SigV4 дозволяє до 7 днів — рівно тиждень;
- краще: **CloudFront signed URL** (власна пара ключів, будь-який строк, бакет лишається
  приватним через OAC);
- або посилання на свій API (`/reports/2026-W41`), який перевіряє вхід користувача і в момент
  кліку віддає redirect на свіжий presigned URL на кілька хвилин. Посилання тоді «вічне», але
  доступ контролюється, і його можна відкликати.
