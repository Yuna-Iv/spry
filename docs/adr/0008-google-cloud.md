# ADR 0008: Spry's core on Google Cloud

- Status: accepted
- Date: 2026-11-21

## Context

Spry runs on AWS in eu-central-1: the React frontend in S3 behind CloudFront, the FastAPI backend
as a container on Lambda (Lambda Web Adapter, function URL), PostgreSQL 17 on RDS (db.t4g.micro,
20 GB, private subnets: the Free plan cannot create Aurora), sign-in with Cognito, a weekly report
(EventBridge Scheduler → SQS → Lambda → S3 → Lambda → SES) and an agenda parser (Lambda → Bedrock).
CloudFormation and Terraform (HCP Terraform workspace `spry-dev`) describe it.

Lab 9 asks what it takes to run the same system on Google Cloud and what it costs. Constraints:

- **The Free Trial**: $300 for 90 days; no GPUs, and the credit pays for neither the Gemini API in
  AI Studio nor partner models (Claude) on Vertex AI.
- **No long-lived keys**, as on AWS since Lab 7: no service account JSON key anywhere.
- **The core first**: the frontend, the API and the database. Sign-in, the report and the parser
  are stretch goals.
- **Cloud SQL never pauses.** It bills by the hour until it is stopped or deleted.

## Decision

| Spry on AWS | On Google Cloud | Decision | Why |
|---|---|---|---|
| S3 + CloudFront, static frontend | Firebase Hosting | replace | CDN and a managed certificate included, free plan; `/api/**` rewrites to Cloud Run, so one origin and no CORS |
| Lambda + function URL, FastAPI | Cloud Run | replace | runs the same image without the Lambda adapter; HTTPS URL; scales to zero |
| ECR | Artifact Registry | replace | 0.5 GB free; a cleanup policy keeps the 3 newest images |
| RDS PostgreSQL db.t4g.micro | Cloud SQL for PostgreSQL 17, db-f1-micro, Enterprise edition, 10 GB SSD | replace | same engine: no code changes, migrations run on container start |
| Cognito user pool + Google | stays on AWS | keep | users and their passwords live in the pool and cannot be exported; Firebase URLs are added to its callback URLs (`extra_app_urls`) |
| EventBridge Scheduler, SQS, report Lambdas, S3 | stays on AWS | keep (for now) | stretch goal: Cloud Scheduler → Cloud Run job |
| SES | stays on AWS | keep | Google Cloud has no e-mail service; a multicloud architecture is allowed |
| Bedrock (Claude Haiku 4.5) | stays on AWS | keep | the trial credit does not pay for Claude on Vertex AI; the parser is stateless and called from the browser |
| SSM Parameter Store | Secret Manager | replace | the whole `DATABASE_URL`, generated by Terraform, readable only by the API's service account |
| CloudWatch Logs | Cloud Logging | replace | automatic for Cloud Run |
| IAM roles | service accounts + IAM roles | replace | `spry-api` runs the API (Cloud SQL Client, one secret); a separate one for Terraform |
| Terraform aws provider, workspace `spry-dev` | google provider, workspace `spry-gcp`, folder `gcp/` | add | its own state: one plan can never break both clouds |

**The database.** Cloud SQL db-f1-micro, stopped when not in use (`make gcp-db-stop`, Terraform
variable `db_running = false`). Running all month it costs about $9.40; stopped, $1.70 for the disk.

- *Not Firestore.* Meetings, participants (many-to-many), agendas and users are relational and
  scoped by owner. Firestore would cost $0 at our traffic but means rewriting the models, the
  queries and the Alembic migrations, and designing documents around every screen.
- *Not the AWS database across clouds.* RDS sits in private subnets with no public access; opening
  it to the internet is a security regression. Each request makes several queries, each crossing
  us-central1 ↔ eu-central-1 (~100 ms), and AWS bills egress.
- *Not a Cloud SQL instance around the clock* during the lab: nobody uses it at night.

**E-mail.** The weekly report stays on AWS with SES. If it moves, the provider is SendGrid or
Mailgun and its API key lives in Secret Manager, readable only by the report's service account.

**Not moved: sign-in, the report, the parser.** They work with the frontend on Google Cloud once
its two addresses are in `extra_app_urls`. The report reads the AWS database, so it does not see
meetings created on Google Cloud: the two deployments have separate data.

**Credentials.** On a laptop, `gcloud auth application-default login`, optionally impersonating the
`spry-terraform` service account (`terraform_service_account`). In CI, Workload Identity Federation
for GitHub Actions, with an attribute condition on the numeric repository and owner IDs. No keys.

## Consequences

- The same Docker image runs in three places: `docker compose`, Lambda (`--target lambda`, the
  default) and Cloud Run (`--target base`, `linux/amd64`). The only code change is the port:
  `--port ${PORT:-8000}`.
- `gcp/deploy.sh` (`make gcp-deploy`) builds and pushes the image, points Cloud Run at it and
  deploys the frontend to Firebase Hosting.
- The API keeps at most 10 database connections (2 instances × pool 2 + overflow 3), within
  db-f1-micro's limit.
- Two clouds, two states, two bills. A request from the Google Cloud frontend still crosses to AWS
  for sign-in and for the parser.
- Cloud SQL must be stopped by hand (or by a scheduled job) when not in use; a forgotten instance
  is the most likely surprise on the bill.

## Alternatives considered

- **Everything on Google Cloud at once** (Identity Platform, Cloud Scheduler, Gemini): more to
  rewrite, and the users would have to sign up again.
- **Cloud Storage + a load balancer for the frontend**: a bucket alone serves no HTTPS on a
  custom domain, and the load balancer bills by the hour.
- **AlloyDB**: Aurora-like, but far larger than Spry needs.
